## 工作流（本地直 commit 模式）

**直接在 `sprint/2026-05-14` 分支上 commit，不开 sub-branch、不发 PR。**

### 每次开干

```bash
# 1. 确认在对的分支
git status                                     # 看 "On branch sprint/2026-05-14"

# 2. 改代码...

# 3. 跑门禁
pnpm verify:gray                               # 必须全绿

# 4. 暂存 + 提交
git add <相关文件>                              # 不要 git add . —— 防止误带文件
git commit -m "feat(scope): xxx (BE-NNN)"
```

### Commit message 规范（强制）

```
<type>(<scope>): <一句话描述> (<工单 ID>)
```

- `type`: feat / fix / refactor / test / docs / chore / infra
- `scope`: server / api / web / admin / shared / scripts
- 必须带工单 ID（`BE-135` / `INFRA-104` / `FE-120` 等）
- 一个 commit 一件事，便于事后回滚

例子：

```
feat(api): X-Internal-Token verification middleware (BE-142)
fix(web): useChat messages move to zustand store (FE-120)
infra: wire INTERNAL_TOKEN to Worker secrets (INFRA-104)
```

### 红线（不允许）

- ❌ 跳过 `pnpm verify:gray` 强 commit
- ❌ `--no-verify` skip git hooks
- ❌ commit message 不带工单 ID
- ❌ 一个 commit 改超过 1 个工单（会让回滚变地狱）
- ❌ 代码或 commit message 里 hardcode INTERNAL_TOKEN 真实值
- ❌ 改 `apps/server/src/routes/{auth,pay/*,db/*,llm/providers/*}.ts`——ADR-0008 明确保留的 stub，Phase 5 上线时才接
- ❌ 在 main 分支上 commit 业务代码（main 只接 sprint 合并；规划文档可直 commit main）

## ⚠️ 必读：BE-142 ↔ BE-135 commit 顺序

**不能反过来。**

```
1. BE-142 先 commit (INTERNAL_TOKEN_REQUIRED=false，向后兼容)
2. BE-135 commit (边缘开始注入 X-Internal-Token)
3. INFRA-104 部署 (两端 token 配齐相同值)
4. 翻 INTERNAL_TOKEN_REQUIRED=true (真正生效)
5. 验收: curl 直连 Node 后端 → 401，走 Worker → 200
```

同机轮流干的话，这条顺序就是工单做的先后顺序。BE-135 之前先确认 git log 里有 BE-142 的 commit。
